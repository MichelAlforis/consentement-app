# i18n — Système multilingue

> Mis à jour : 2026-04-26  
> Statut : **FR / EN / ES opérationnels** — conformité 100% (audit Sprint 17-18)

---

## Pourquoi un système custom et pas `next-intl`

`next-intl` repose sur le routeur URL de Next.js (`/fr/…`, `/en/…`). Cette app utilise :
- un **routeur maison** (état React, pas d'URL)
- Capacitor avec `output: 'export'` (fichiers statiques — pas de middleware)

Résultat : `next-intl` est incompatible. Le système implémenté est un **React Context custom** qui ne touche pas l'URL, ne nécessite aucun middleware, et fonctionne tel quel dans le WebView Capacitor.

## Architecture

```
app/
  context/
    LanguageContext.tsx          ← Provider + useLanguage()
  i18n/
    index.ts                     ← useTranslation() hook
    locales/
      fr/
        ui.ts          ← navigation, headers, barre démo, thème
        onboarding.ts  ← welcome, âge, auth, intro
        home.ts        ← home adulte, home mineur, accompagnement
        spaces.ts      ← PersonalSpace, DuoSpace + toutes les étapes Duo
        education.ts   ← Learn, Help, PornoVsRéalité, Loi, Quiz
        games.ts       ← GamesHub, DiceGame, GooseGame, CardGame, Premium
        data.ts        ← données structurées : comfort, levels, quiz, loi, diceCategories
        index.ts       ← merge des 7 namespaces + export type Translations
      en/              ← même structure × 7 fichiers + index.ts
      es/              ← même structure × 7 fichiers + index.ts
```

**3 locales × 7 fichiers + 3 index = 24 fichiers de locale.**

Le type `Translations` est inféré depuis `fr/index.ts` — c'est le FR qui fait foi pour la structure.

## Flux de données

```
useAppState          →  language: Language ('fr' | 'en' | 'es')
                         changeLanguage(lang) → setLanguage + localStorage
        ↓
page.tsx             →  <LanguageProvider language={language} changeLanguage={changeLanguage}>
        ↓
LanguageContext      →  fournit { language, changeLanguage } à tout l'arbre
        ↓
useTranslation()     →  charge le dict de la locale active + fallback FR
        ↓
t('clé.dot.notation') → string résolu
```

## `useTranslation()` — comportement exact

```typescript
// app/i18n/index.ts
export function useTranslation() {
  const { language } = useLanguage();
  const dict = translations[language] ?? translations.fr;  // fallback si locale inconnue
  const fallback = translations.fr;

  function t(key: string, params?: Record<string, string | number>): string {
    const value = getNestedValue(dict, key)
      ?? getNestedValue(fallback, key);   // fallback clé manquante → FR
    if (value === undefined) return key;  // ultime fallback → la clé elle-même
    if (typeof value === 'string') return params ? interpolate(value, params) : value;
    return key;
  }

  return { t, language };
}
```

**`getNestedValue`** — résout la notation dot sur objets **ET tableaux** :
```typescript
// Clé  'quiz.0.question'  →  accède à quiz[0].question
// Clé  'data.levels.3'    →  accède à levels[3]
// Clé  'comfort.tenderness.items.kisses'  →  objet imbriqué normal
function getNestedValue(obj, path) {
  return path.split('.').reduce((current, key) => {
    if (current !== null && current !== undefined && typeof current === 'object') {
      return current[key];
    }
    return undefined;
  }, obj);
}
```

**Interpolation** — syntaxe `{param}` :
```typescript
// Template : "Accord #{count} — vous avez dit oui ensemble."
t('gooseGame.accord.accordNum', { count: 3 })
// → "Accord #3 — vous avez dit oui ensemble."

// Template : "{name}, c'est ton vote"
t('gooseGame.accord.yourVote', { name: 'Marie' })
// → "Marie, c'est ton vote"
```

## Utilisation dans un composant

### Patron de base

```tsx
'use client';
import { useTranslation } from '../../i18n';  // ajuster le chemin relatif

export function MonComposant() {
  const { t } = useTranslation();

  return (
    <div>
      <h1>{t('monNamespace.titre')}</h1>
      <p>{t('monNamespace.description')}</p>
    </div>
  );
}
```

### Avec interpolation

```tsx
// Dans la locale FR :
// partnerExploring: '{name} explore ses zones de confort...'

<p>{t('duo.filling.partnerExploring', { name: partnerName })}</p>
```

### Avec pluralisation (pattern utilisé dans l'app)

Il n'y a pas de système pluriel intégré. On utilise du JS inline + deux clés :

```tsx
// Clés FR :
// accordBadge: 'accord'
// accordBadgePlural: 'accords'

<span>{count} {count > 1 ? t('gooseGame.accordBadgePlural') : t('gooseGame.accordBadge')}</span>

// Autre pattern (zone / zones) :
<p>{totalCommon} {totalCommon > 1 ? t('duo.summary.zones') : t('duo.summary.zone')}</p>
```

### Avec HTML dans une chaîne (dangerouslySetInnerHTML)

Réservé aux cas où le HTML vient entièrement du fichier de locale, **jamais** pour interpoler des entrées utilisateur :

```tsx
// Clé FR : intro: "Les jeux sont conçus pour <strong>explorer le consentement</strong>"
<p dangerouslySetInnerHTML={{ __html: t('games.intro') }} />
```

### Accès aux tableaux (data namespace)

```tsx
// data.levels est un tableau : ["Non", "Pas maintenant", "Curieux·se", "À l'aise", "J'adore"]
t(`data.levels.${value}`)  // value = 0..4

// data.quiz est un tableau d'objets
t(`data.quiz.${index}.question`)
t(`data.quiz.${index}.options.${optionIndex}`)
t(`data.quiz.${index}.explanation`)
```

### Accès aux catégories du dé

```tsx
// diceCategories est un objet indexé par numéro de face (1..6)
t(`diceCategories.${faceNumber}`)   // → 'Osez', 'Parlez', 'Et si…', etc.

// Dans CardGameScreen et ActivityOverlay :
t(`diceCategories.${currentCard.deck}`)
t(`diceCategories.${currentSquare.face}`)
```

### Accès aux items de comfort (ComfortSlider, DuoFillingStep, etc.)

```tsx
// comfort est dans le namespace data
t(`comfort.${categoryKey}.title`)
t(`comfort.${categoryKey}.description`)
t(`comfort.${categoryKey}.items.${item.id}`)

// categoryKey = 'tenderness' | 'intensity' | 'trust'
// item.id = 'kisses' | 'cuddles' | 'massage' | ... (voir data.ts)
```

## Ajouter une clé de traduction

**Étape 1 — Identifier le bon namespace** (voir carte ci-dessus)

**Étape 2 — Ajouter la clé dans `fr/[namespace].ts`**

```typescript
// fr/games.ts
export const games = {
  // ...
  cardGame: {
    // ...
    maNouvelleCle: 'Mon texte en français',
    // Si interpolation :
    avecParam: 'Bonjour {name}, tu as {count} cartes',
  },
};
```

**Étape 3 — Ajouter la clé dans `en/[namespace].ts` et `es/[namespace].ts`**

Respecter **exactement** la même structure — TypeScript n'enforce pas les clés EN/ES (cast `as unknown as Translations`), c'est votre responsabilité.

**Étape 4 — Utiliser dans le composant**

```tsx
t('cardGame.maNouvelleCle')
t('cardGame.avecParam', { name: 'Léa', count: 5 })
```

**Aucune étape supplémentaire** — pas de build step, pas de codegen, pas de registre.

## Ajouter une nouvelle locale (ex: Allemand)

**1.** Déclarer le type dans `app/types/index.ts` :
```typescript
export type Language = 'fr' | 'en' | 'es' | 'de';
```

**2.** Créer `app/i18n/locales/de/` avec les 7 fichiers + `index.ts` (copier EN comme base)

**3.** Importer dans `app/i18n/index.ts` :
```typescript
import { de } from './locales/de';
const translations: Record<Language, Translations> = {
  fr, en, es, de: de as unknown as Translations,
};
```

**4.** Exposer dans le sélecteur de langue (UI)

## Changer la langue — state et persistance

La langue est gérée dans `useAppState` :

```typescript
// app/hooks/useAppState.ts
const [language, setLanguage] = useState<Language>('fr');

// Chargement depuis localStorage au boot
useEffect(() => {
  const saved = localStorage.getItem('language') as Language;
  if (saved && ['fr', 'en', 'es'].includes(saved)) setLanguage(saved);
}, []);

// Changement
const changeLanguage = (lang: Language) => {
  setLanguage(lang);
  localStorage.setItem('language', lang);
};
```

Le `LanguageProvider` est monté dans `app/page.tsx` et enveloppe tout l'arbre.

**À implémenter :** un sélecteur de langue (boutons FR / EN / ES) dans les paramètres. Il suffit d'appeler `changeLanguage(lang)` depuis `useLanguage()`.

## Pièges connus

### 1. La clé retourne la clé elle-même

La clé n'existe ni dans la locale active ni dans FR. Vérifier orthographe + namespace.

```
// Écran affiche "cardGame.maNouvelleCle" au lieu du texte
// → la clé n'a pas été ajoutée dans fr/games.ts
```

### 2. `t()` appelé hors du `LanguageProvider`

Erreur silencieuse — `language` vaut `'fr'` (valeur par défaut du Context). Vérifier que le composant est bien dans l'arbre sous `<LanguageProvider>`.

### 3. Collision de clés entre `education.ts` et `data.ts`

`data.ts` est spreadé en **dernier** dans `fr/index.ts`. Si une clé dans `data.ts` porte le même nom qu'une clé dans `education.ts`, la version data (tableau) écrase la version education (objet de strings UI).

**Règle** : les clés UI des écrans éducatifs utilisent le suffixe `Screen` pour éviter la collision :

| Namespace data (tableaux) | Namespace education (UI) |
|---------------------------|--------------------------|
| `quiz.0.question` → data | `quizScreen.validate` → UI |
| `loi.0.titre` → data | `loiScreen.title` → UI |
| `pornoVsRealite.0.porno` → data | `pornoVsRealiteScreen.inPorno` → UI |

**Symptôme** : `t('quiz.validate')` retourne `"quiz.validate"` (clé absente car le tableau écrase l'objet).

### 4. Accès tableau en notation dot — ne pas oublier le fix

Le `getNestedValue` gère les tableaux via clé numérique string (`'0'`, `'1'`…). **Ne jamais remettre le guard `!Array.isArray(current)`** qui cassait cet accès.

```typescript
// ✅ Correct
t('levels.3')  // → "À l'aise"
t('quiz.0.question')

// ❌ Ne fonctionne pas
t('levels')    // retourne la clé — c'est un tableau, pas une string
t('data.levels.3')  // 'data' n'est pas une clé racine après le spread
```

### 5. HTML dans les chaînes — XSS

`dangerouslySetInnerHTML` uniquement avec des clés de locale statiques. **Jamais** pour interpoler `{name}` avec une entrée utilisateur :

```tsx
// ❌ Dangereux — name vient de l'utilisateur
dangerouslySetInnerHTML={{ __html: t('key', { name: userInput }) }}

// ✅ Sécurisé — interpoler le name séparément, en JSX
<p>{t('key')}{' '}<strong>{userName}</strong></p>
// ou : utiliser deux clés (pre + post)
```

### 6. `as const` dans les fichiers de locale

Tous les fichiers de locale terminent par `} as const`. Cela rend les types ultra-stricts (string littéraux). Si vous voyez une erreur de type sur un import de locale, c'est souvent un `as const` manquant.

### 7. Chemin après spread — `games.xxx` pas `games.games.xxx`

Le fichier `games.ts` exporte `{ games: {...}, diceGame: {...}, ... }`. L'index merge par spread `{ ...games }`. Après spread, la clé racine dans le dict est `games` (le nom de la sous-clé dans l'export), **pas** `games.games`.

```typescript
// ✅ Correct
t('games.free')          // → 'Gratuit'
t('games.dice.title')    // → 'Le Dé du Consentement'
t('games.includedFree')  // → 'Inclus · accès libre'

// ❌ Incorrect — games.games n'existe pas dans le dict mergé
t('games.games.free')         // → retourne la clé (undefined → fallback key)
t('games.games.includedFree') // → retourne la clé
```

**Règle mnémotechnique :** le chemin dans `t()` = nom de la clé de premier niveau dans l'export `.ts` + `.` + chemin interne. Jamais le nom de la variable d'export.

```typescript
// Dans games.ts : export const games = { games: { free: 'Gratuit' } }
// → variable d'export : 'games'  (ignorée dans t())
// → clé de premier niveau : 'games'  (premier segment de t())
// → chemin interne : 'free'
// → t('games.free') ✅
```

### 8. EN et ES ne sont pas type-checked structurellement

Le cast `as unknown as Translations` permet à EN/ES d'avoir des clés manquantes sans erreur TypeScript. Le fallback FR s'affiche à la place. **Vérification manuelle nécessaire** pour chaque nouvelle clé ajoutée.
